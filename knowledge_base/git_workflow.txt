# Git: система контроля версий

Git — это распределённая система контроля версий, разработанная для отслеживания изменений в файлах и координации работы нескольких разработчиков над одним проектом. Создана Линусом Торвальдсом в 2005 году для разработки ядра Linux.

## Основные концепции Git

### Репозиторий
Репозиторий — это хранилище, содержащее историю изменений проекта. В Git каждый разработчик имеет полную локальную копию всего репозитория со всей историей.

### Коммит
Коммит — это снимок состояния файлов в определённый момент времени. Каждый коммит имеет уникальный хеш SHA-1 и содержит:
- Идентификатор автора
- Дата и время
- Сообщение коммита
- Ссылку на родительский коммит
- Изменённые файлы

### Ветвление
Ветка — это независимая линия разработки. Git позволяет создавать новые ветки для разработки новых функций, исправления ошибок или экспериментов, не затрагивая основную кодовую базу.

### Слияние (Merge)
Merge — это операция объединения изменений из одной ветки в другую. Git умеет автоматически объединять изменения, если они не конфликтуют.

### Pull Request / Merge Request
Pull Request (PR) или Merge Request (MR) — это предложение объединить изменения из одной ветки в другую. Обычно сопровождается обсуждением и код-ревью.

## Установка и настройка Git

### Установка

**Linux (Debian/Ubuntu):**
```bash
sudo apt update
sudo apt install git
```

**macOS:**
```bash
brew install git
```

**Windows:**
Скачайте установщик с официального сайта git-scm.com

### Первоначальная настройка

После установки необходимо настроить имя и email:

```bash
git config --global user.name "Ваше имя"
git config --global user.email "ваш.email@example.com"
```

Проверить конфигурацию:
```bash
git config --list
```

## Основные команды Git

### Начало работы

```bash
git init                    # Создать новый репозиторий
git clone <url>             # Клонировать существующий репозиторий
```

### Подготовка изменений

```bash
git status                  # Показать состояние рабочей директории
git add <file>              # Добавить файл в индекс
git add .                   # Добавить все изменения
git add -p                  # Добавить изменения по частям
git reset <file>            # Убрать файл из индекса
git restore <file>          # Отменить изменения в файле
```

### Фиксация изменений

```bash
git commit -m "Сообщение"   # Создать коммит с сообщением
git commit -am "Сообщение"  # Добавить и закоммитить отслеживаемые файлы
git commit --amend          # Изменить последний коммит
```

### История коммитов

```bash
git log                     # Показать историю коммитов
git log --oneline           # История в одну строку
git log --graph             # История в виде графика
git log --all               # История всех веток
git show <commit>           # Показать детали коммита
git diff                    # Показать изменения в рабочей директории
git diff <commit1> <commit2> # Показать различия между коммитами
```

## Ветвление в Git

### Создание и переключение веток

```bash
git branch <branch-name>    # Создать ветку
git checkout <branch-name>  # Переключиться на ветку
git switch <branch-name>    # Переключиться на ветку (новый синтаксис)
git checkout -b <branch>    # Создать и переключиться на новую ветку
git switch -c <branch>      # Создать и переключиться на новую ветку
```

### Список веток

```bash
git branch                  # Локальные ветки
git branch -a               # Все ветки (включая удалённые)
git branch -r               # Только удалённые ветки
```

### Слияние веток

```bash
git merge <branch-name>     # Слить ветку в текущую
git merge --no-ff <branch>  # Создать merge-коммит даже если fast-forward возможен
```

### Разрешение конфликтов

При слиянии Git может обнаружить конфликты — ситуации, когда одна и та же строка была изменена в разных ветках.

```bash
git status                  # Показать конфликтующие файлы
# Отредактируйте файлы, чтобы разрешить конфликты
git add <resolved-files>    # Отметить конфликты как разрешённые
git commit                  # Завершить слияние
```

### Удаление веток

```bash
git branch -d <branch>      # Удалить ветку (если она слита)
git branch -D <branch>      # Принудительно удалить ветку
```

## Работа с удалёнными репозиториями

### Удалённые репозитории

```bash
git remote -v                # Показать удалённые репозитории
git remote add <name> <url>  # Добавить удалённый репозиторий
git remote remove <name>     # Удалить удалённый репозиторий
```

### Получение изменений

```bash
git fetch                    # Получить изменения из удалённого репозитория
git pull                     # Получить и слить изменения
git pull --rebase            # Получить изменения и перебазировать
```

### Отправка изменений

```bash
git push                     # Отправить текущую ветку
git push -u origin <branch>  # Отправить ветку и установить upstream
git push --force             # Принудительно отправить (осторожно!)
git push --force-with-lease  # Безопасное принудительное push
```

## Перебазирование (Rebase)

Rebase — это альтернатива merge, которая перезаписывает историю коммитов.

```bash
git rebase <branch-name>     # Перебазировать текущую ветку на указанную
git rebase -i HEAD~3         # Интерактивный rebase последних 3 коммитов
```

### Интерактивный rebase

Интерактивный rebase позволяет изменять, объединять, удалять или переупорядочивать коммиты:

```bash
git rebase -i HEAD~5         # Редактировать последние 5 коммитов
```

В открывшемся редакторе можно использовать команды:
- `pick` — использовать коммит как есть
- `reword` — изменить сообщение коммита
- `edit` — остановиться для редактирования коммита
- `squash` — объединить с предыдущим коммитом
- `fixup` — объединить, но отбросить сообщение
- `drop` — удалить коммит

## Отмена изменений

### Отмена незафиксированных изменений

```bash
git restore <file>           # Отменить изменения в файле
git restore .                # Отменить все изменения
git restore --staged <file>  # Убрать из индекса, но сохранить изменения
```

### Изменение последнего коммита

```bash
git commit --amend           # Изменить последний коммит
git commit --amend --no-edit # Изменить, но не менять сообщение
```

### Отмена коммитов

```bash
git revert <commit>          # Создать новый коммит, отменяющий изменения
git reset --soft HEAD~1      # Удалить коммит, оставить изменения в индексе
git reset --mixed HEAD~1     # Удалить коммит, оставить изменения в рабочей директории
git reset --hard HEAD~1      # Удалить коммит и все изменения (опасно!)
```

## Stash (Контекстное хранилище)

Stash позволяет временно сохранить незафиксированные изменения:

```bash
git stash                    # Сохранить изменения в stash
git stash list               # Показать список stash
git stash apply              # Применить последний stash
git stash apply stash@{2}    # Применить конкретный stash
git stash pop                # Применить и удалить последний stash
git stash drop               # Удалить последний stash
git stash clear              # Удалить все stash
```

## Теги (Tags)

Теги используются для标记 важных моментов истории, обычно релизов:

```bash
git tag                      # Показать все теги
git tag <tag-name>           # Создать lightweight тег
git tag -a <tag-name> -m "Сообщение"  # Создать annotated тег
git show <tag-name>          # Показать информацию о теге
git push origin <tag-name>   # Отправить тег
git push origin --tags       # Отправить все теги
git tag -d <tag-name>        # Удалить локальный тег
git push origin :refs/tags/<tag-name>  # Удалить удалённый тег
```

## Git-flow и другие модели ветвления

### Git-flow
Классическая модель ветвления с постоянными ветками:
- `main` — production-ready код
- `develop` — интеграционная ветка
- `feature/*` — новые функции
- `release/*` — подготовка релизов
- `hotfix/*` — исправление критических ошибок

### GitHub Flow
Простая модель:
- `main` всегда deployable
- Каждая функция создаётся в отдельной ветке
- Pull Request для обсуждения
- Merge после code review

### Trunk-based Development
Все разработчики работают в одной основной ветке:
- Краткоживущие ветки для функций
- Feature flags для не завершённых функций
- Непрерывная интеграция

## Лучшие практики Git

1. **Частые коммиты** — делайте небольшие, логические коммиты
2. **Осмысленные сообщения** — пишите ясные, описательные сообщения
3. **Не коммитьте чувствительные данные** — пароли, ключи API, сертификаты
4. **Используйте .gitignore** — не засоряйте репозиторий временными файлами
5. **Обновляйте рабочую копию** — регулярно делайте pull
6. **Используйте Pull Requests** — все изменения через код-ревью
7. **Не коммитьте сломанный код** — main ветка должна быть стабильной
8. **Используйте branches для функций** — каждая функция в отдельной ветке
9. **Не rebase публичные ветки** — перезаписывайте только локальную историю
10. **Пишите тесты** — тесты должны коммититься вместе с кодом

## Продвинутые техники

### Cherry-pick
Применение конкретного коммита к текущей ветке:
```bash
git cherry-pick <commit-hash>
```

### Bisect
Бинарный поиск для нахождения коммита, сломавшего функциональность:
```bash
git bisect start
git bisect bad HEAD
git bisect good <commit-hash>
# Git автоматически переключится между коммитами
# Проверяйте, сломанная ли функциональность
git bisect good/bad
git bisect reset
```

### Reflog
Журнал всех изменений HEAD:
```bash
git reflog                  # Показать историю изменений HEAD
git reflog show <branch>    # История изменений конкретной ветки
git reset --hard HEAD@{2}   # Откатиться на 2 изменения назад
```

### Worktree
Работа с несколькими ветками одновременно:
```bash
git worktree add ../project-feature feature-branch
# Теперь можно работать в двух директориях одновременно
git worktree remove ../project-feature
```

## Git Hooks

Git hooks — это скрипты, которые выполняются на определённых этапах работы Git:

### Клиентские hooks
- `pre-commit` — перед созданием коммита
- `commit-msg` — проверка сообщения коммита
- `post-commit` — после создания коммита
- `pre-push` — перед отправкой в удалённый репозиторий

### Серверные hooks
- `pre-receive` — перед получением push на сервер
- `post-receive` — после получения push
- `update` — для каждой ветки перед обновлением

Пример pre-commit hook для запуска линтера:
```bash
#!/bin/sh
npm run lint
```

## Мониторинг и отладка

```bash
git blame <file>            # Показать, кто и когда изменил каждую строку
git bisect                  # Найти коммит, сломавший функциональность
git log --grep="pattern"    # Найти коммиты по сообщению
git log -S "function_name"  # Найти коммиты, добавлявшие/удалявшие строки
git shortlog -s -n          # Статистика по авторам
git archive --format=tar.gz --prefix=project/ HEAD | gzip > project.tar.gz  # Создать архив
```

## Восстановление после ошибок

### Откат последнего коммита
```bash
git revert HEAD             # Создать новый коммит, отменяющий изменения
git reset --soft HEAD~1     # Удалить коммит, сохранить изменения
```

### Восстановление удалённой ветки
```bash
git reflog                  # Найти хеш удалённой ветки
git branch <branch-name> <commit-hash>  # Восстановить ветку
```

### Восстановление потерянных коммитов
```bash
git fsck --lost-found       # Найти потерянные объекты
git show <object-hash>      # Проверить содержимое объекта
git branch recovery <hash>  # Создать ветку из найденного коммита
```
